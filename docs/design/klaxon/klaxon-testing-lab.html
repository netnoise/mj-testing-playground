Klaxon Testing Lab

An Angular incident board where no test is trusted until it has caught a real defect. The app exists to host bugs; the tests exist to prove they notice.

frontend testing is the point audience: colleagues unit of work: one defect → which layer caught it
01  Why

The repo already makes the argument

Three tests in src/app/app.component.spec.ts pass today. Two of them are worth nothing, and the second one is worth less than nothing.

src/app/app.component.spec.ts:20 
expect(app).toBeTruthy();

Green whether the component renders correctly, renders blank, or throws in ngOnInit.

src/app/app.component.spec.ts:33 
expect(compiled.querySelector('.app-header h1').textContent)
  .toContain('mj-testing-playground');

Rename that CSS class in a stylesheet — no behaviour change — and it goes red. Demote the <h1> to a styled <div> — a real accessibility regression — and it stays green. Inverted: fails on cosmetics, passes on defects.

That is the standard state of frontend test suites, generated or hand-written. A repo of example patterns does nothing about it, and a model in your editor writes those patterns faster than you can look them up anyway. A repo of experiments does something about it, because an experiment has a result that cannot be generated — only run.

02  Mechanism

One defect, every layer, one recorded finding

This is the loop the whole repo turns on. Everything else — the app, the backend, the component choices — exists to make this loop produce interesting results.

Mutation testing (Stryker) automates the cheap half of this: it plants hundreds of defects and reports what fraction your suite catches. The hand-planted defects above are for the cases Stryker can't express — a semantic regression, a timezone assumption, a lost debounce.

04  The app

Klaxon — an on-call board, chosen for difficulty

Features are picked because they are hard to test, not because they are useful. An incident board is unusually rich: it is live, dense, time-sensitive, and has genuine accessibility stakes — someone reads it at 3am under pressure.

Feature Exercises Why it resists testing
Incident board asyncperfa11y Live updates arriving mid-interaction; virtualised rows; grid semantics; sort stability
Triage & escalation form formsa11y Cross-field rules, async validation, dialog focus traps, unsaved-changes guard
Incident archive perfa11y Server-side vs client-side pagination, page-size drift mid-fetch, "jump to page" vs infinite scroll, keyboard nav across pages
Incident timeline asyncperf Streamed appends, relative timestamps that go flaky at midnight, optimistic acks
Findings showcase the point The table in section 03, rendered from recorded runs — and itself under test

Deferred: on-call rota (the calendar-grid keyboard model and DST-boundary recurrence rules) is real work but doesn't need to block the first loop — nothing in §01–03 depends on it. It re-enters the build sequence once the archive and its pagination patterns have produced their first findings.

The archive is the deliberate long-table case: same incident data, but paged rather than virtualised, so it forces the pagination failure modes a scrolling list never hits — an item disappearing off the current page because a live update reordered the set underneath the reader, a page number that outlives the data it pointed at, "Page 3 of 12" going stale mid-read, and a "Next" control that a screen reader announces with no indication anything changed. Good material for the same plant-a-defect loop: mutate the page-size guard, mutate the aria-live region on page change, see which layer notices.

05  Control

The backend is a control variable — and something has to make it noisy

One real Node BFF, plus MSW handlers implementing the same contract. Run the identical suite against both. The suite must not be able to tell them apart — and when it can, you've located implementation coupling you didn't know you had.

The generator is the "deliberately hostile backend" idea made concrete, and it's why Go re-enters after being ruled out for the contract itself (§06): many independent simulated monitors, each misbehaving on its own schedule (one flaps every few seconds, another goes silent, a third emits duplicates), fan concurrently into one event stream. That's what goroutines and channels are for, and it's the same reason real synthetic-monitoring and chaos-injection tools are commonly written in Go rather than reinvented in whatever language the frontend happens to use. Angular never knows it exists — it only ever sees the BFF's shaped output.

06  Decisions

Settled, with reasons

Angular
Regenerate on the current major Standalone, signals, new control flow, zoneless from day one. The repo is a near-empty scaffold on 14.3 — there is nothing to preserve, and none of the modern idioms exist there.
Migration
One feature, built old then migrated Not six majors of ng update. Build one Klaxon feature NgModule-and-RxJS style, migrate it to standalone/signals, measure which tests survived. That's the part happening without you at work.
Components
Material, plus one hand-rolled rival on CDK Material everywhere (work-realistic), except one complex widget built twice. Same tests against both reveals exactly how much a11y Material was quietly doing for you.
Contract
Node BFF + MSW, one contract, two runtimes Kotlin stays out entirely — a third implementation of the same contract is upkeep without a new finding. Go was ruled out here for the same reason, then re-entered with a different job (below): it's not a second backend, it's what feeds the first one.
Event generator
Go, behind the BFF, never called by Angular Concurrent, independently-misbehaving simulated monitors fanning into one stream is goroutines' actual home turf — genuinely awkward to hand-write correctly in single-threaded Node. Testable in isolation with Go's own table-driven tests, which becomes an honest technique comparison for the showcase rather than a shipped feature nobody asked for.
Findings
In-app /showcase route You send one URL. The showcase reads recorded run data — and being a dense interactive table, it's a legitimate test subject in its own right.
07  Order

Build sequence

  1. Modern baseline Regenerate on the current Angular major; port nothing but advanced-form's validators, which are the only real logic in the repo. Harness gates green before anything else lands.
  2. One feature, fully instrumented The incident board alone, with all five layers wired: Jest, Testing Library, Playwright, axe, visual. Resist adding feature two until every layer runs in CI.
  3. Event generator, behind the BFF The Go service: one goroutine per simulated monitor, fault injection on a schedule, feeding the Node BFF only. MSW is built against the same contract in parallel and never touches it — this is what makes the incident board's "live" feel real instead of a fixed fixture.
  4. First three planted defects Heading demotion, colour-only severity, lost debounce. Record the results by hand. This is the moment the repo becomes worth having — before any showcase UI exists.
  5. Showcase route Render the findings table from recorded data. Only now, once there's something true to show.
  6. Mutation testing Stryker over the Angular specs, plus Go's own mutation tool over the generator, for a coverage number that measures catching, not executing. Expect it to be humbling on both sides.
  7. Remaining features, then the rivals Triage form, incident archive, timeline. Then the Material-vs-CDK widget pair and the old-vs-migrated feature — the comparisons, as byproducts. On-call rota returns after these.
08  Doors

Needs you, not an agent

Three things in this plan an agent can't do alone under your own harness rules.

door 1
Every dependency in steps 1 and 3. The Angular major bump, Testing Library, MSW, axe, Stryker, and the Go module itself (go.mod, its own toolchain version) — each is a one-way door under .ai/HARNESS.md. They want stating and deciding, not asking.
door 7
angular.json is gate-scope config. The test builder, the .sass→.scss switch, new budgets — all live in a file the budget hook blocks agents from touching. A human edit gates step 1, whichever path you take.
rule
A planted defect must never be silently removed. The repo's value is the record. Defects get reverted in a commit that also records the finding, or the whole thing degrades into a normal demo app within a month.
